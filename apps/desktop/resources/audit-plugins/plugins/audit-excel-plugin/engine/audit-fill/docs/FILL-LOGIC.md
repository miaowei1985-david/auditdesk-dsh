# 填表逻辑（v0.1，2026-11-23）

目标：把 `~/Documents/审计底稿/<客户>/` 的客户资料填进所里的 `AI审计软件测试手工底稿`，每一步可追溯、可复核、可回退。

---

## 一、总体链路

```
客户资料                      规范化                    模板                        验证
科目余额表 ──┐
财务报表   ──┼─→ 统一口径数据 ─→ 结构识别 ─→ 填数 ─→ 公式重算 ─→ 勾稽比对 ─→ 报告
凭证/明细账 ─┘   (TB/FS/vouchers)  (表头/输入区)  (只写输入格)  (formulas)   (TB↔审定表↔报表)
```

三条铁律：

1. **只写输入格**：模板里凡是公式格一律不写，避免把「审定表←明细表」的链条写死。
2. **每个数都有依据**：写入时同时记 `basis`（来源科目/报表行/计算式），生成填写清单。
3. **算不出来就不填**：缺账龄表、缺盘点表、缺合同证据的格留空，并写入「待取证」，绝不凭估计填数。

## 二、客户数据规范化（已完成部分）

### 2.1 文件识别

14 家公司 79 个文件里，**25 个扩展名与实际格式不符**：

| 实际格式 | 数量 | 说明 |
|---|---:|---|
| 真 xlsx（后缀 .xls） | 5 | openpyxl 按扩展名拒绝，必须按魔数读 |
| HTML 伪装的 .xls | 20 | 统一能科等系统导出；用 pandas.read_html |
| OLE2 真 .xls | 29 | xlrd 读 |
| PDF | 1 | 集瑞船务报表，需另行 OCR/解析 |

`reader.py` 按魔数分流并统一成二维网格；`xlsx` 一律走 BytesIO，绕开扩展名校验。

### 2.2 科目余额表 → 统一账户模型

不同客户导出的表头差异极大（用友 UFPrn、金蝶、SAP B1、台湾账户式、HTML、科目汇总表）。做法：

1. **表头定位**：前 40 行里找同时含「科目/余额/发生/期初」的行，再向下吞并 1–2 行子表头（借方/贷方/原币/本位币）。
2. **列角色识别**：每列解析成 `(group, side, unit)`：
   - group：期初 / 期末 / 本期发生 / 本年累计
   - side：借方 / 贷方 / 金额 / 方向
   - unit：本位币 / 原币 / 未标注
3. **合并单元格补全**：Excel 合并表头只在左上角存值，「期初余额」跨 4 列时后 3 列会丢失分组——按行做标签前向填充复原。
4. **方向列**：`借/贷`、`+/-`、`±` 按位置归属（期初的方向列管期初，余额的方向列管期末）。
5. **统一符号**：`期末 = 期初 + 借方发生 − 贷方发生`，借方为正。
6. **去重**：
   - 多币种行：优先「综合本位币/本位币/本币/人民币」行；
   - 辅助核算行（供应商/客户/部门/项目）：有汇总行用汇总行，无汇总行才把明细行加总；
   - 同一科目多行：取有金额的那行（有些导出会留一行空壳）。
7. **层级**：按科目编码前缀建父子关系，一级科目 = 无父节点。

### 2.3 已知口径差异（必须处理，否则填错）

| 现象 | 客户 | 处理 |
|---|---|---|
| 3 位旧制度编码（101 现金 / 102 银行存款 / 111…） | 同进、乐线 | 编码不可直接用，按**科目名称**映射 |
| 无科目编码（只有中文名+英文名） | 安堡罗 | 按名称映射，代码由映射表补 |
| 科目汇总表（按科目分段列流水，不是余额表） | 虹盛 | 需专用适配器：取每段「期初余额」「本期合计」「本年累计」 |
| 多币种/外币 | 丸金、赞富、统一能科、维曼 | 必须取「综合本位币」列；原币填明细表原币栏，汇率单独取 |
| xls 文件损坏标记 | 机施教育 | xlrd 需 `ignore_workbook_corruption=True` 或先转 xlsx |

## 三、模板结构识别

模板是 2006 年前后鼎信诺系底稿改的，特点是：**审定表全是公式，数据入口在明细表**。

以 `货币资金` 为例（已实测）：

- 审定表 B/D/E/F/G 列全部是公式：`D9=货币资金明细表!I28`，`E9=…!L28`，`B9=D9-C9`，`B11=B8+B9+B10`。
- 明细表输入格：`G`(期初原币) `H`(汇率) `J`(期末原币·调整前) `K`(汇率)，以及 `B/C/D/E/F` 描述列。
- 计算格：`I=G*H`，`L=ROUND(J*K,2)`，小计 `I28=SUM(I16:I27)`，`合计 I35=I12+I28+I34`。

因此引擎必须先识别「哪些是输入格」，只写这些格；写完用 `formulas` 重算，审定表自然出数。

### 结构识别规则

1. 表头行：含「项目/期初/期末/调整前/调整后/借方/贷方」的行；
2. 输入格判定：**无公式** 且 属于金额列（B–G 中数值/货币格式），并排除小计合计行；
3. 分段识别：以「XX序号 / 开户银行 / 项目」为段头，段内 `1..n` 为数据行，遇「小计/合计」止；
4. 列语义从段头三行解析（原币/汇率/本位币 × 期初/期末·调整前/调整/调整后），**不写死列字母**。

## 五、跨表勾稽（每份底稿必跑）

1. 明细表合计 == 审定表未审数（重算后）
2. 审定表合计 == 客户报表对应行（容差 0.01）
3. 报表恒等式：资产总计 == 负债 + 所有者权益
4. TB 恒等式：Σ期初 + Σ借 − Σ贷 == Σ期末（行级逐行检查）
5. 底稿间：5 个工作簿同一科目审定数一致

任一项不过，写入报告并标「差异来源待查」，不静默通过。

## 十、v0.4 追加：损益类（2026-11-23 第四轮）

### 10.1 核心口径：取发生额单边，不能轧差

年结时每个损益科目都做了结转分录，**借贷两边金额相等**（如营业收入贷方 726,754.91、借方也是 726,754.91），
按「借−贷」计算会全部归零。规则：

- 收入类（6001/6051/6301/6111）取 **贷方发生额**；
- 成本费用类（6401/6402/6403/6601/6602/6603/6711/6801）取 **借方发生额**；
- 费用科目里的收入性质明细（利息收入、汇兑收益、补贴）取 **−|贷方|**，冲减费用。

### 10.2 各表填法

| 底稿 | 填法 |
|---|---|
| 营业收入明细表 | 主营/其他两段，收入填 B 列、成本填 E 列；行数按「小计」行位置推导（模板 A 列不写序号） |
| 税金及附加审定表 | 单一税种填对应行（印花税等），多税种按名称匹配 |
| 管理费用/销售费用/财务费用审定表 | 按明细项目名与 TB 子科目名双向包含匹配，写 B 列本期数 |
| 所得税费用审定表 | 当期/递延按子科目名归行，写 B 列 |
| 审定表合计 | 全部由模板公式汇总，不写 |

- 明璞 4/4、安堡罗 5/6、舜壹 4/6、丸金 4/6、赞富 3/6 一致；

## 十四、v0.8 追加：未分配利润 + 科目映射收口（2026-11-23 第八轮）

### 14.1 未分配利润的填法

表结构：期初（B8）→ 净利润（B13）→ 利润分配（B15 公积金 / B16 股利 / B17 其他）→ 期末（B21 公式）。

做法：**以 TB 的期初/期末为准，倒推净利润**：
```
净利润 = 期末 − 期初 + 分配
```
- 期初 = −(4104 期初 + 4103 期初)，期末 = −(4104 期末 + 4103 期末)，贷方为正；
- 分配：提取盈余公积取 4101 贷方发生；股利取凭证 4104 且摘要含「股利/分红」的借方；
- 净利润先按此倒推，再与损益表净利润比，差额写进备注，不硬调。

实测四家全部与报表一致：中天 9,272,652.39、丸金 −2,463,337.94、明璞 −1,204,926.87、舜壹 −48,327,001.30。

### 14.2 科目解析必须「名称优先、代码闭嘴」

舜壹账套里 **4104 = 工程施工**（钢材/水泥/工资等明细），按代码映射会把 3.8 亿工程成本灌进利润分配。
改为：**有名称时只信名称，名称解析不到就不映射**，子科目由父科目继承；代码只用于「无名称」的兜底
（旧制度 3 位码 101/102 仍保留）。

这条规则同时修好了舜壹的权益合计（1,672,998.70 与报表一致）。

## 十七、v0.11 追加：待取证清单（2026-11-23 第十一轮）

### 17.1 为什么要出这份清单

底稿填到后面，真正的风险不是「填错数」，而是**用了假设却没告诉人**。所以把三类问题自动汇总成一份可发给客户的 PBC 清单：

1. **报表与底表差异**：TB 算出来和报表对不上（例如中天固定资产差 133,337.15）；
2. **底稿与报表差异**：填完的审定表与报表对不上；
3. **填写假设**：填写清单里带「暂/未取得」的单元格，按表聚合。

每条都给出「需补充资料」——按科目映射到标准取证清单（账龄表、卡片、对账单、申报表、决议…）。

## 十八、v0.12 追加：两种列报口径与重分类备注（2026-11-23 第十二轮）

### 18.1 往来「净额 vs 重分类」两种口径都算

客户报表有的做了往来重分类（丸金：应收/预收分开列），有的没做（中延：代领个人款 280,000 留在其他应付款）。

结果：中延资产 111,458,752.03、负债 106,833,829.09 与报表**完全一致**；同进 2,442,696,444.85 也一分不差。

## 二十、v0.14 追加：现金流量表直接法原型（2026-11-23 第十五轮）

### 20.1 方法

模板 J 工作簿是 .xls（无法写），所以先做**分析原型**，等转换后回填。

1. 现金科目 = 1001 / 1002 / 1012；
2. 凭证按顺序分组——用友导出里后续行常不带凭证号，归到上一张凭证（这一步不做，中天会出现一笔 −2,612 万的「无号凭证」）；
3. 每张凭证净现金变动 = Σ现金借方 − Σ现金贷方；
4. 按凭证内非现金科目归类：长期资产→投资、借款/权益→筹资、其余→经营；
5. **自校验：三类合计 = 现金净变动**。

### 20.2 结果

| 公司 | 经营 | 投资 | 筹资 | 合计 | 现金净变动 | 差异 |
|---|---:|---:|---:|---:|---:|---:|
| 中天 | −20,129,745.51 | 0 | 0 | −20,129,745.51 | −20,129,745.51 | 0 |
| 中延 | −10,073,953.39 | 0 | 1,450,000.00 | −8,623,953.39 | −8,623,953.39 | 0 |
| 丸金 | −265,351.99 | 0 | 0 | −265,351.99 | −265,351.99 | 0 |
| 舜壹 | 9,131,133.04 | 0 | −6,995,516.25 | 2,135,616.79 | 2,135,616.79 | 0 |
| 集瑞船务 | −856,483.81 | 0 | 0 | −856,483.81 | −856,483.81 | 0 |
| 赞富 | 2,073,463.02 | 0 | −4,747,528.98 | −2,674,065.96 | −2,468,496.45 | −205,569.51 |
| 维曼 | 8,535,549.12 | 0 | 0 | 8,535,549.12 | 1,349,858.59 | 7,185,690.53 |

5 家完全一致；赞富差 205,569.51（本位币日元 vs 凭证人民币）、维曼差 7,185,690.53（凭证口径与 TB 不一致，和收入差 1,563 万同源）。

### 20.3 局限

- 整张凭证归类，混合投资+经营的单据会被整笔归投资；
- 现金等价物只含 1001/1002/1012；
- 模板 J 仍是 .xls，回填要等转换。

### 20.4 顺带解决

- 凭证解析新增「按 TB 编码表映射」：银行子户名（工行/建行…）不带「银行存款」字样时也能正确归类；
- 用友摊平格式的空凭证号行按顺序归组，避免把所有无号行并成一张巨额凭证。

## 二十九、v0.23 追加：账龄改为凭证 FIFO 实算（2026-11-23 第二十四轮）

### 29.1 从假设到实算

之前应收/其他应收账龄拿不到账龄表，只能「暂全额列示 1 年以内」。现在用凭证算：

1. 期初余额视为 2024-12-31 的一笔，落到「1-2 年」；
2. 按日期逐笔处理：借方（开票/发生）新增一笔，贷方（收款）按 **FIFO** 冲最早的；
3. 贷方先于借方出现（预收）时记负批次，后续借方先冲负批次；
4. 年末剩余批次按日期落到 1年以内 / 1-2年 / 2-3年 / 3年以上。

### 29.2 校验与效果

- 每个账户「四段合计 = TB 期末余额」，丸金、中天全部账户 0 差异；
- 明细表 J-M 列与审定表四段都按实算填，模板自带的核对列（G − 明细表合计）= 0；
- 丸金填写清单里「暂列 1 年以内」出现次数 **从 15 降到 0**，账龄全部有凭证依据。

### 29.3 局限

- 期初余额统一按 1-2 年处理（没有 2024 年凭证，无法再细分）；
- 目前只做了应收/其他应收（借方余额类）。应付/预收需要反向 FIFO（贷方为发票、借方为付款），下一轮补。

### 29.4 代码

`auditfill/aging.py`：`buckets_for(entries, opening, code)` + `aging_by_account(tb, entries, std)`；
在 `fill_counterparty` 里传入 `aging=` 即启用，未传时仍用原来的假设模式（保证没凭证的客户可用）。

## 三十、v0.24 追加：应付/预收的反向账龄（2026-11-23 第二十五轮）

### 30.1 反向 FIFO

负债类科目方向相反：**贷方是新发生的应付（发票），借方是付款**。`buckets_for(..., liability=True)`
把「贷方新增、借方冲销」按日期做 FIFO；期初余额同样视为 2024-12-31 的一笔（1-2 年）。

### 30.2 无明细凭证时的兜底

- 否则：有发生额 → 全部落 1 年以内并标注；无发生额（期初=期末）→ 落 1-2 年（因为期初是上年结转）。

### 30.3 应用范围

应收账款、其他应收款（借方）；应付账款、预收款项、其他应付款（贷方）。
`run_company.py` 在凭证可用时自动传入，凭证不可用时仍走「暂列 1 年以内」的旧逻辑。

### 30.4 校验

每个账户四段合计 = TB 期末余额（中天、中延全部账户 0 差异）；审定表四段合计与报表一致。

## 三十一、v0.25 追加：固定资产按类别填（2026-11-23 第二十六轮）

### 31.1 什么时候能分类

TB 里固定资产有按类别设置的子科目时（电子设备、办公设备、运输工具…），就按类别填；

### 31.2 两个坑

1. **关键词顺序**：第一版把「电子设备」判成了「机器设备」，因为 `机器设备` 的关键词含「设备」，

2. **累计折旧段的行标题是公式**：A19 显示 `=A10`，按文本匹配不到「电子设备」。
   解析时若标题是 `=A{n}`，回读 A{n} 的标签再匹配。

另外聚合只用**叶子科目**，避免父科目（固定资产总额）与子科目重复计算。

### 31.3 效果

### 31.4 局限

仍缺资产卡片，无法细分到「房屋/机器/运输」时只能归「其他」；折旧年限、残值率等卡片信息也没有。

## 三十五、v0.29 追加：交付前质量检查与「不覆盖公式」硬约束（2026-11-23 第三十轮）

- 填写记录（basis）入库，等于自动留痕。

### 40.2 结构

| 表 | 内容 |
|---|---|
| company | 公司、期间、三个源文件路径 |
| account | 科目（code/name/std/level/is_leaf/期初/借/贷/期末） |
| fs_line | 客户报表行（end/begin） |
| voucher | 凭证分录（日期/科目/摘要/金额） |
| audit_check | 勾稽结果（calc/fs/diff/hint） |
| fill | 每个填写单元格的值与依据 |

`is_leaf` 很关键：不做叶子标记时，父科目与子科目一起 SUM 会把金额算成 2 倍
（第一版 1002 货币资金 8,402.15 被查成 16,804.30）。

### 40.3 现状

- 10 家公司全部入库，约 3.1 MB；
- 科目 1,927 行、报表行 686 行、凭证 18,513 行、勾稽 170 项、填写 2,354 条；
- 跨公司查询（10 家 × 5 科目）耗时 **0.00 秒**。

### 40.4 能做什么

1. **跨公司对比**：同一科目谁高谁低、谁没这个科目（如乐线没有应收账款）；
2. **差异归集**：所有 diff≠0 的勾稽项一屏看完，按金额排序；
3. **复核留痕**：每个数字都能查到它写进哪个工作簿、哪个单元格、依据是什么；
4. **增量更新**：客户补资料后只重灌那一家，不用全量解析。

## 四十四、v0.38 追加：应交税费差异的根因（2026-11-23 第四十轮）

### 44.1 根因

不是填表逻辑错，是客户 TB 自身「总账行 ≠ 子科目合计」：

| 公司 | 总账余额 | 子科目合计 | 差 |
|---|---:|---:|---:|
| 丸金 | −13,761.07 | 16,343.48 | 30,104.55 |
| 明璞 | −10,933.19 | −10,353.20 | 579.99 |

模板的明细表是 `H = C + 应交 − 已交`（按子科目逐税种填），审定表 `=SUM(E8:E18)`，
所以填出来的合计只能等于**子科目合计**，不可能等于总账——除非人为补一笔差额。

### 44.2 试过的补差方案（未采用）

在「其他税费」行的 C 列加 `target − current`：
- 数学上成立（中天、丸金、明璞都验算过目标值正确）；
- 但落到 Excel 后，实际合计与目标不一致，说明审定表/明细表的行映射并非简单的 8–18 ↔ 9–19；
- 且会误伤中天（原本 −9,657.29 正确），已回退。

结论：在摸清审定表每行到底引用哪一行之前，不动。当前状态是：
- 中天、中延、丸金（明细合计口径）等仍按子科目填；
- 丸金/明璞的应交税费与总账差 30,104.55 / 579.99，已在差异归因里标为「客户 TB 总账≠子科目」。

### 44.3 什么是确定的

- 中天的应交税费重算 **−9,657.29 = 报表**，说明正常客户的链路是对的；
- 差异只出现在总账与明细本身不一致的客户，属于**客户资料问题**，需要客户确认以哪个为准。

## 四十五、v0.39 追加：差异三分法（2026-11-23 第四十一轮）

### 45.1 口径

以前把「报表没有这一行」也算成差异（diff 为空），导致报告里“丸金 12/15、明璞 7/14”看起来有问题。
现在分三类：

| 类别 | 定义 | 处理 |
|---|---|---|
| 勾稽一致 | diff = 0 | — |
| 实质差异 | diff ≠ 0，客户资料/口径/币种 | 要客户补或确认 |
| 列报差异 | diff ≠ 0，但同一笔在另一行或总额/净额不同 | 不追 |
| 报表无此行 | 客户报表本身没有该行（diff 为空） | 不算差异 |

| 丸金 | 12 | 0 | 0 | 3 |
| 同进 | 12 | 0 | 3 | 3 |

| 舜壹 | 15 | 1 | 0 | 3 |
| 维曼 | 10 | 5 | 0 | 2 |
| 乐线 | 5 | 5 | 1 | 2 |
| 安堡罗 | 7 | 9 | 0 | 3 |
| 赞富 | 4 | 12 | 0 | 3 |

结论修正：
- **丸金、明璞其实没有实质差异**（之前的差额都是「报表无此行」）；

## 四十七、v0.41 追加：赞富多币种的真相与交付说明（2026-11-23 第四十三轮）

### 47.1 赞富不是「日元本位币」，是「多币种 + 综合本位币续行」

期间 科目代码  科目名称   币别     期初余额(借) ...

## 四十八、v0.42 追加：多币种「综合本位币」续行解析（2026-11-23 第四十四轮）

### 48.1 格式

### 65.1 从「工具」到「流程」

用户的要求是：这些 Excel 能力要**结合在审计工作流里**，不是孤立的功能按钮。
做法是把每家客户自动定位到流程阶段，工具按阶段给动作：

| 阶段 | 名称 | 判定条件 | 下一步动作 |
|---:|---|---|---|
| 1 | 资料接收 | 无填写记录 | `audit_fill_process` |
| 2 | 底稿填制 | 有填写、无勾稽 | 勾稽随填表返回 |
| 3 | 勾稽核对 | 有勾稽结果 | 看差异 |
| 4 | 差异处理 | 存在实质差异 | 补资料/确认口径 |
| 5 | 出具备忘录 | 实质无差异、无备忘录 | `audit_memo` |
| 6 | 复核 | 备忘录已生成 | 复核后归档 |

阶段由数据推导（不靠人工打勾），所以不会出现「状态说已完成、数据其实没有」的假象。

### 65.2 当前分布

```
中天、中延、丸金、同进、明璞、舜壹、维曼、安堡罗、统一能科 → 阶段 6 复核
乐线（7 项）、赞富（4 项）、机施教育（3 项）→ 阶段 4 差异处理
```

### 65.3 备忘录

`audit_memo` 生成每家一页审计备忘录：资料来源、执行情况、未解决差异、待取证、
结论（可出具 / 不宜直接出具）。结论按实质差异是否为 0 自动判定。

### 65.4 与 DSH 的衔接

对话里问「各家到哪一步了」→ `audit_workflow`；
问「哪些能出报告」→ 阶段 6 即实质无差异且有备忘录。
工具、数据库、流程三者是同一份数据的不同视图。

## 六十六、v0.60 追加：复核留痕与归档阶段（2026-11-23 第六十八轮）

### 66.1 stage 7

新增 `review` 表：复核人、备注、时间、复核时的勾稽快照。
流程阶段因此从 6 个变成 7 个：

```
资料接收 → 底稿填制 → 勾稽核对 → 差异处理 → 出具备忘录 → 复核 → 归档
```

判定：有备忘录但未签字 → 阶段 6；已签字 → 阶段 7，并显示复核人与时间。

### 66.2 为什么快照

签字时把「当时的一致/实质差异计数」存进 `snapshot`，日后若数据变化，
能证明复核针对的是哪一版底稿，而不是「现在这版」。

### 66.3 工具

`audit_review`：传 company + reviewer + note 即登记；只传 company 则查看历史。

实测：
```
登记 中天 → {"reviewer":"项目组","snapshot":{"fills":197,"checks":18,"ok":18,"sub":0}}
audit_workflow 中天 → 阶段 7 归档，已由 项目组 复核（2026-11-23T15:11:02）
```

### 66.4 备忘录同步

备忘录新增「复核留痕」一节，结论之前列出复核人与时间。

## 六十七、v0.61 追加：把审计流程写进 Agent 的系统提示（2026-11-23 第六十九轮）

### 67.1 问题

前面做的阶段机只是「工具返回的状态」，模型未必照着走——可能跳过勾稽直接出备忘录。

### 67.2 做法

插件在 `apply` 里注册一个 `systemPrompt.section`（`inject: ['tools','systemPrompt']`），
把五条流程约束写进每次会话的系统提示：

1. 按阶段走：资料接收→底稿填制→勾稽核对→差异处理→出具备忘录→复核→归档；
2. 提到某家客户先 `audit_workflow` 看阶段，再按 next 行动，不跳步；
3. 工具分工：填表 / 状态 / 备忘录 / 复核 / 台账；
4. 差异三分类：实质（要补）、列报（不追）、报表无此行（不算）；
5. 数字必须可追溯，缺资料就说缺。

### 67.3 效果

流程不再是「工具说明书」，而是 Agent 的行为约束：**任何会话进来都先定位阶段，再动手**。

### 67.4 边界

这是全局注入，所有会话都会看到这段提示；如果只想在特定预设里生效，
应改为 agent preset 的 prompt section（见 DSH compositions 文档）。

## 六十八、v0.62 追加：底稿变动留痕（2026-11-23 第七十轮）

### 68.1 做法

`fill` 表每次装载前，先读出上一版的值，与新值逐格比较，不同则写入 `change` 表：

```
company / workbook / sheet / cell / old_value / new_value / changed_at
```

这样客户改资料后重跑，能回答「这次改了什么」，而不是只看到最终结果。

### 68.2 验证

手工把中天固定资产明细表 B17 从 142,221.20 改成 142,222.20，再跑 `load_db`：

```
中天 固定资产明细表!B17: 142,222.20 → 142,221.20
```

记录正确（重跑把错误值改回真值，正好形成一条新旧对照）。测试数据已清空。

### 68.3 工具

`audit_changes`：按公司查看最近变动，默认 50 条；无变动时返回「暂无变动记录」。

### 68.4 与流程的关系

- 差异处理、客户补资料后重跑，变更自动落在 `change` 表；
- 复核时（`audit_review`）除勾稽快照外，还可对照 change 记录判断改了什么；
- 归档后若数据再变，change 时间戳可作为「归档后是否被动过」的线索。

## 六十九、v0.63 追加：带「+/-」方向列时的符号重复反转（2026-11-23 第七十二轮）

### 69.1 现象

机施教育的余额表有 `+/-` 方向列，且金额本身已写成负数：

```
科目编码 科目名称   +/-  期初余额  …  +/-   余额
2206    应交税金   借   954,274.30 …  贷   -116,443.42
```

解析时先按方向列（贷）取负，金额本身又是负数，**两次取负变成正数**，
于是应交税费 116,443 变成了资产方向，与报表（负债 116,443）符号相反。

### 69.2 修法

1. 方向列按 role 精确取用：begin 用 `begin/direction`、move 用 `move/direction`、end 用 `end/direction`，
   不能笼统用 `dirs[0]` / `dirs[-1]`（机施的 end 方向列在最前面，会取错）；
2. **金额已带符号（<0）时不再按方向翻一次**。

### 69.3 效果

- 机施教育：应交税费 −116,443.42（贷方），与报表一致；勾稽 **3 → 0 差异**，8/8 一致；
- 中天、丸金、统一能科、赞富等不受影响（这些表金额不带负号，走原逻辑）。

### 69.4 当前 12 家

机施清零后，**10 家实质无差异**，只剩乐线 7、赞富 5 两项客户资料问题。

## 七十一、v0.65 追加：乐线其他应收从差 1,134 万降到 5.8 万（2026-11-23 第七十四轮）

### 71.1 发现

乐线报表「其他应收款」1,522.30 万，TB 只有 Suspense 388.48 万。差额 1,133.82 万来自三个
**英文名、无标准科目**的账户：

```
121401 Long-term loans - third parties      10,000,000.00
121405 Long-term loans - other related        775,000.00
121501 Long-term refundable Deposits          505,218.00
```

加上 1221 后合计 15,164,996.78，与报表只差 58,000（其他流动资产）。

### 71.2 修法

别名补 `long-term loan(s)`、`refundable deposit` → 1221；
`long-term prepaid` → 1801（否则「Other long-term prepaid expenses」被错认成预付账款，
导致预付款项虚增 305 万）。

### 71.3 效果

- 其他应收：差 1,133.82 万 → **5.8 万**；
- 预付款项：一度虚增 305 万，修正后回到 133,320.30（与报表仍差 49.35 万，属科目归集）；
- 自检从 16 项扩到 **17 项**（新增 1221 断言），全部通过。

### 71.4 教训

英文科目名必须**先长后短**匹配：「long-term prepaid」里含「prepaid」，
若先命中短别名就会归错科目。已知别名索引按长度倒序，新增别名时要确认这一点。

## 七十三、v0.67 追加：往来负数不能凭空消失（2026-11-23 第七十六轮）

### 73.1 问题

赞富应收账款底稿 7,875,484.82，总账 6,163,044.84，多 171 万。

原因：`routed_items` 对本科目**只保留正向余额**，把 33 个客户里若干贷方余额（合计 1,712,439.98）
直接丢掉了——既没进应收，也没进预收，钱凭空消失。

### 73.2 修法（按客户报表列报决定）

- 若客户报表**有预收款项余额**（如丸金 558,793.54）：负数重分类到预收（原逻辑）；
- 若报表**没有预收行/为 0**（如赞富）：负数留在应收里按净额列示。

实现：`keep_negatives` 参数由 `fs.get("预收款项")` 决定，同时作用于应收与预收两张明细表，避免重复。

### 73.3 效果

- 赞富应收账款 6,163,044.84 = 总账 = 报表；勾稽 11/5 → **12/4**；
- 丸金（报表有预收）仍走重分类，12/0 不变；
- 中天 18/0 不变；自检 17 项全过。

### 73.4 教训

「过滤负数」这种防御性写法会把钱弄丢。往来科目的负数有两种归属（本科目净额 / 对方科目重分类），
必须由**报表列报**决定，而不是一律丢弃。

## 七十四、v0.68 追加：按报表净额/总额决定往来归属，11 家清零（2026-11-23 第七十七轮）

### 74.1 规则

同一对往来科目（应收/预收、应付/预付、其他应收/其他应付），负数余额有两种去处：

| 客户报表列报 | 处理 |
|---|---|
| 有对应科目余额（如丸金有预收、中天有预付） | 负数**重分类**到对方科目 |
| 只有一边、按净额列示（如赞富） | 负数**留在本科目**，不重分类 |

判定方式：比较报表该科目金额与 TB 净额，接近（1% 内）即视为净额列报。

### 74.2 追加两处

- 其他应收/其他应付：赞富报表其他应付 = TB 净额 → 净额列示；同时把「预付 269 万并入其他应收」按报表补一条带备注的重分类；
- 应付/预付：同理，避免预付贷方 4,200 被重分类进应付。

### 74.3 分位舍入

差异 < 0.02 视为一致（0.01 的舍入不算差异），避免「未分配利润差 1 分」这种噪音。

### 74.4 结果

| 公司 | 之前 | 现在 |
|---|---|---|
| 赞富 | 11/5 | **16/0** |
| 中延 | 11/2 | **13/0** |
| 同进 | 12/3 | **14/1** |
| 安堡罗 | 7/9 | **9/7** |
| 乐线 | 8/7 | 8/7（待客户资料） |

**12 家里 11 家实质无差异**，只剩乐线 7 项（缺应收科目与科目范围）。

## 七十五、v0.69 追加：客户与项目模型（2026-11-23 第七十八轮）

### 75.1 为什么要

用户要的不是「12 家跑完」，而是把方法**装进客户与项目管理**：
一个客户可有多个项目（期间/业务类型），资料、底稿、阶段都要按项目隔离。

### 75.2 模型

```
client ──< project ──< project_file
                     └── 阶段（资料接收…归档）
```

- 项目代码：`<客户>-<期间>`；
- 2025 项目沿用 `out/<客户>/底稿包`，其他期间输出 `out/<客户>/<期间>/底稿包`，互不覆盖。

### 75.3 迁移

现有 12 家公司 → 12 个客户 + 12 个 2025 年报审计项目，资料路径迁入 `project_file`。

### 75.4 新增工具

`audit_clients`、`audit_project_create`、`audit_project_attach`、`audit_project_run`。

实测（演示客户已清理）：

```
audit_project_create 测试客户 2026  → 测试客户-2026
audit_project_attach 测试客户-2026 tb/fs → 2 个文件
audit_project_run 测试客户-2026 → 勾稽 7/14 一致，阶段推进到「勾稽核对」
```

### 75.5 兼容

旧的 `audit_fill_process` / `audit_status` / `audit_memo` 仍可用；它们按「公司」工作，
与项目模型共用同一份底稿数据（project 通过客户代码关联 company）。
